Case study · Obigo, Seoul

Automated reporting for an insurance partnership

In May 2026, an at-home car-maintenance service from Obigo's group launched inside a major Korean insurer's app. I built the system that reports on it every day and every week, without anyone running it by hand.

First 16 days of unattended operation, starting July 21, 2026.

The problem

Every week, one person collected the numbers by hand, pasted them into PowerPoint, and emailed the report to the insurer. It took the same time every week, problems only showed up in the next week's report, and each new partner would have added the same work again.

The goal was a report that nobody has to run, which arrives on schedule even when the data is late or an API fails.

What I built

Five steps run in order, and a scheduler starts them on its own.

1CollectBigQuery · GA4Pull the day's app events, reservations, and reviews. Save the raw data.
2ComputePython · pandasKPIs, funnel, intervals, and chart values. Every number is made here.
3WriteClaude APIShort text in fixed slots: title, status, evidence, priority.
4CheckRulesBlock overclaiming. Confirm page count, fonts, and chart values.
5DeliverPDF · email · messengerDaily message and a weekly 4-page PDF by email. Every send is logged.
If the LLM fails or breaks a rule, template sentences built from the same numbers take its place.
SchedulerRuns the steps up to 8 times a day, remembers which dates are still pending, and sends an alert if two days fall behind.

Built before the data arrived. Access to the data came much later than planned. I built the report layout, delivery tests, and fallback paths on dummy data first, so when access arrived I only had to connect it.

Key decisions

  • Code computes the numbers. The LLM writes the words.

    KPIs, conversion rates, intervals, and even chart coordinates are calculated in Python. The model only receives the finished metrics, and it can't change a number, a chart, or the layout. This lowers the risk of made-up figures and ties token use to the number of reports instead of the amount of data.

  • If the LLM fails, the report still goes out.

    Generated text is checked against rules that block exaggerated claims. If it breaks a rule, or the API call fails, the report uses template sentences built from the same metrics. It reads plainer, but it's correct and on time.

  • Try eight times a day and remember what's pending.

    The data export didn't arrive at the same time every day. The scheduler checks every two hours from 10:00 to midnight, saves which dates are still pending, and picks up where it left off after a restart.

  • Keep the raw data.

    Raw pulls are saved as NDJSON before any processing. When a metric definition changed, I could recompute past reports without querying BigQuery again.

What I'd improve next

  • Check that every number the LLM writes matches the computed metrics. Today the rules check wording and structure only.
  • Log how often the fallback is used, and alert if it keeps happening.
  • Add real-time incident alerts. They were planned but not shipped, because the partner's systems didn't collect the signals they needed.

Case study · University Hospital Limerick, Ireland

Comparing kidney disease across 33 European countries

The research team wanted to see how Ireland compares with the rest of Europe on chronic kidney disease, and how long nephrology patients, including children, wait to be seen. I turned 15+ years of public data into a report they could explore on their own.

Role
Research Intern
Timeline
May – Jul 2025
Data
Eurostat, Irish waiting lists
Tools
R, tidyverse, Plotly, leaflet, Quarto

The challenge

The sources coded countries, years, and diseases in slightly different ways. On top of that, a country with an older population has more kidney disease simply because of age, so comparing raw rates would mix up age with health.

What I did

  1. Made the sources match

    Aligned country codes, years, and ICD-10 disease groups across hospital-discharge and cause-of-death data.

  2. Adjusted for age

    Reweighted each country's rates to the same standard population, so the differences reflect health instead of age structure.

  3. Made it explorable

    Built an interactive Quarto report. Pick a country to see its hospitalization and mortality trends and its place on the map, next to the EU average.

What it delivered

The team got a reproducible, filterable view of 33 countries in place of one-off static charts. Waiting lists are tracked by how long patients have waited: 0–6, 6–12, 12–18, and 18+ months. I also presented the 33-country comparison to support the team's ongoing research.

Case study · Purdue AI Omics Lab

Validating lab data before machine learning

Dr. W. Andy Tao's AI Omics team uses high-resolution mass-spectrometry data to search for disease biomarkers with machine learning. Before any model can learn from that data, the data has to be consistent.

Role
Project Team Member
Timeline
Sep 2025 – Apr 2026
Team
AI Omics research lab
Tools
Python, R, Django, Git

The challenge

Files arrived in different structures from one experiment to the next. Data that hadn't been checked couldn't safely go into model training.

1Raw filesMass-spectrometry output, structured differently by experiment
2Structure checksRule-based checks and error handling in Python. This was my part.
3Standardized dataOne consistent format across experiments
4ML researchBiomarker models trained on checked data

What I did

  • Wrote modular Python processing code with file handling and clear error handling.
  • Added rule-based checks that confirm each experiment's structure before the data moves on.
  • Built inside the lab's shared Django backend, working through Git feature branches with the team.

Why it matters

A model is only as reliable as its inputs. These checks give the lab a validation step before training, which keeps preprocessing stable and the research reproducible.
